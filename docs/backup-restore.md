# بک‌آپ، بازیابی و کش

در پنل ادمین سه گزینه وجود دارد:

- **🔌بک آپ**: خروجی کامل `pg_dump` از دیتابیس PostgreSQL، شامل schema، داده، sequence، index و تنظیمات مالکیت و دسترسی همان دیتابیس. این گزینه بک‌آپ کل cluster یا roleهای سراسری PostgreSQL نیست.
- **📦 بک‌آپ داده‌ها**: خروجی فشردهٔ `jsonl.gz` فقط از داده‌های شش جدول ربات، بدون schema. داده به صورت streaming و از یک snapshot ثابت خوانده می‌شود. نسخهٔ ۲ فایل شامل تعداد رکوردها و SHA-256 است؛ مقادیر باینری، IDهای ۶۴ بیتی و زمان UTC بدون تغییر حفظ می‌شوند. این گزینه روی PostgreSQL و SQLite کار می‌کند.
- **♻️ بازیابی بک‌آپ**: آپلود، اعتبارسنجی، پیش‌نمایش تعداد رکوردها و سپس تأیید داخل ربات. بازیابی تمام داده‌های فعلی ربات را جایگزین می‌کند. گزینهٔ بازگشت، پیش‌نمایش را لغو می‌کند؛ پیش‌نمایش پس از ۳۰ دقیقه منقضی می‌شود.

## قالب‌های ورودی

| ورودی | پشتیبانی |
| --- | --- |
| دامپ کامل PostgreSQL با schema | ورود داده به schema فعلی Alembic |
| `pg_dump --data-only` با COPY | بله، شامل جدول‌های خالی |
| `--inserts` یا `--column-inserts` | بله؛ INSERTهای literal تک‌ردیفی و چندردیفی |
| INSERT بدون نام ستون، بدون schema | ترتیب ستون‌های مدل فعلی و مدل قدیمیِ فاقد last_activity_at / expires_at / max_downloads قابل تشخیص است؛ ترتیب ناشناخته رد می‌شود |
| آرشیو custom (`-Fc`) و tar (`-Ft`) | تبدیل فقط داده با `pg_restore` و اعتبارسنجی همان مسیر |
| SQL.gz، custom.gz، tar.gz | بله، با محدودیت حجم بازشده |
| بک‌آپ دادهٔ ربات، نسخهٔ ۱ یا ۲ | بله؛ نسخهٔ ۲ checksum و پایان فایل را نیز بررسی می‌کند |
| directory archive، ZIP، zstd، بک‌آپ فیزیکی/WAL، SQL دلخواه یا dump کل cluster | پذیرفته نمی‌شود؛ ابتدا خروجی منطقیِ پشتیبانی‌شده تهیه شود |

جدول‌های `alembic_version` و `aerich` از فایل مبدأ وارد نمی‌شوند؛ نسخهٔ migration مقصد حفظ می‌شود. حداقل جدول‌های user، file و channel باید در snapshot مشخص باشند. جدول‌های جدیدترِ اختیاری در بک‌آپ قدیمی می‌توانند خالی باشند. جدول یا ستون دادهٔ ناشناخته، کلید تکراری، مالک ناموجود، تاریخ یا مقدار خارج از محدوده، فایل ناقص و دستور psql ناشناخته باعث رد فایل می‌شوند.

جداول پروژه در schema پیش‌فرض public در نظر گرفته شده‌اند. دامپ با نام schema دیگر با خطای روشن رد می‌شود؛ انتقال خودکار جداول بین namespaceهای سفارشی در این مسیر انجام نمی‌شود.

مالک فایل در مدل فعلی Telegram userid است. اگر schema مبدأ صریحاً به user.id اشاره کند، یا در بک‌آپ فقط داده بتوان این ارتباط را بدون ابهام تشخیص داد، مالکیت با استفاده از کاربران مبدأ به userid تبدیل می‌شود. در صورت ابهام، بازیابی متوقف می‌شود و بک‌آپ دارای schema لازم است.

## اختلاف نسخهٔ PostgreSQL

بازیابی داخل ربات، دادهٔ جداول ربات را به schema جاریِ Alembic وارد می‌کند. DDL، نام owner، ACL، function، extension و SETهای مخصوص نسخهٔ مبدأ اجرا نمی‌شوند. بنابراین وجود schema در دامپ یا تنظیماتی مانند transaction_timeout مانع ورود داده به نسخهٔ دیگر PostgreSQL نمی‌شود. بازیابی داخل ربات، schema سفارشیِ خارج از مدل‌های پروژه را بازسازی نمی‌کند؛ برای بازیابی عین دیتابیس و اشیای سفارشی باید از دامپ کامل و ابزارهای PostgreSQL در یک دیتابیس جدا استفاده کرد.

جدیدترین pg_dump/pg_restore نصب‌شده انتخاب می‌شود؛ مسیر صریح تنظیمات اولویت دارد. برای گرفتن دامپ، pg_dump باید نسخهٔ سرور را پشتیبانی کند. برای خواندن آرشیو، pg_restore باید قالب آرشیو مبدأ را بشناسد؛ نسخهٔ همسان یا جدیدتر معمولاً لازم است. نصب یک client جدیدتر، نیازی به ارتقای سرور ندارد. رفتار و محدودیت‌های native dump/restore در [مستندات pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html) و [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html) آمده است.

انتقال واقعی در هر دو جهت PostgreSQL **16.15 ↔ 18.6** بررسی شده است؛ برای سایر نسخه‌ها اعتبارسنجی داده برقرار است، اما آزمون روی همهٔ نسخه‌های PostgreSQL ادعا نمی‌شود. SQL و schema دلخواهی که امکان تبدیل بدون تغییر معنا ندارند با خطا رد می‌شوند.

## اجرای بازیابی

قبل از تغییر داده، یک بک‌آپ دادهٔ ایمنی ساخته می‌شود. عملیات جاری ربات تمام می‌شوند؛ ورود داده در یک تراکنش انجام می‌شود. PostgreSQL جداول مقصد را قفل می‌کند و داده‌ها با COPY باینری در batchهای ۲۰۰۰ رکورد وارد می‌شوند. SQLite از تراکنش write اختصاصی و batch insert استفاده می‌کند. خطا هنگام ورود داده تمام حذف‌ها و درج‌ها را rollback می‌کند. sequenceهای PostgreSQL اصلاح می‌شوند و سپس ANALYZE اجرا می‌شود.

پس از commit، namespace کش `cutly:*`، گفتگوها، اشیای فایل در گفتگو، لیست محلی کاربران، تنظیمات کانال‌های قفل، پیش‌نویس‌ها و کارهای زمان‌بندی‌شدهٔ ارسال همگانیِ قبلی پاک می‌شوند. بازیابی حین ارسال همگانی فعال رد می‌شود. زمان‌بندی‌های داخل حافظهٔ نسخهٔ قبلی از بک‌آپ قابل بازسازی نیستند؛ همان محدودیت قبلی پروژه برقرار است.

فایل ایمنی `before-restore-*.jsonl.gz` روی سرور حفظ و برای ادمین ارسال می‌شود. شکست در ارسال این فایل، بازیابی commit‌شده را به عنوان شکست دیتابیس گزارش نمی‌کند. فایل آپلودی و spool پیش‌نمایش پاک می‌شوند. فایل‌های بک‌آپ عادی پس از ارسال از سرور حذف می‌شوند. فایل‌های ایمنی باید مطابق سیاست نگهداری اپراتور مدیریت شوند.

اگر Redis هنگام invalidation در دسترس نباشد، خواندن کش در همان process غیرفعال می‌شود و فایل `cache-reset-required` در BACKUP_DIR باقی می‌ماند. اتصال بعدی باید namespace را پاک کند تا دادهٔ قدیمی دوباره استفاده نشود. BACKUP_DIR باید قابل نوشتن و بین restartها پایدار باشد. در حال حاضر اجرای یک process ربات روی دیتابیس فرض شده است؛ چند process مستقل باید برای بازیابی متوقف شوند.

## کش و کارایی

- متادیتای فایل، آدرس تلگرام و اعضای مرتب آلبوم: snapshot نسخه‌دار با TTL پنج دقیقه؛ تغییر هر فایل فقط همان فایل و آلبوم مربوط را باطل می‌کند. cache fill قدیمی پس از تغییر نسخه پذیرفته نمی‌شود.
- شمارنده، انقضا و سقف دانلود: SQL مرجع اصلی است. ارسال‌های در حال اجرا با یک رزرو اتمیک در process، همراه با خواندن مقدار تازهٔ SQL، کنترل می‌شوند تا از سقف عبور نکنند. شمارندهٔ دائمی فقط پس از ارسال موفق با UPDATE اتمیک افزایش می‌یابد؛ رزرو موقت وارد بک‌آپ نمی‌شود و ارسال ناموفق آن را آزاد می‌کند. این کنترل مانند اجرای ربات، برای یک process در نظر گرفته شده است.
- کاربران: کش ID، نقش‌ها و پروفایل حفظ شده؛ فعالیت هر پیام در SQL ثبت و همان timestamp در کش به‌روزرسانی می‌شود. برای هر پیام SELECT دوبارهٔ پروفایل لازم نیست. بررسی عضویت در لیست محلی از set استفاده می‌کند.
- کانال‌های قفل: تنظیمات از Redis و حافظه خوانده می‌شوند و با اضافه/حذف کانال یا بازیابی refresh می‌شوند. عضویت واقعی کاربر همچنان از تلگرام بررسی می‌شود.
- تنظیمات کپشن: خواندن گرم از Redis؛ تغییر تنظیمات نسخهٔ کش را باطل می‌کند.
- آمار: چهار query تجمیعی به جای ده query، با همان پنجره‌های زمانی و فرمول‌های قبلی.
- پاک‌سازی Redis: SCAN و UNLINK در batch، بدون دستور مسدودکنندهٔ KEYS یا حذف کل دیتابیس Redis.
- file_reference منقضی: یک تلاش برای خواندن پیام اصلی از کانال ذخیره‌سازی، ذخیرهٔ reference جدید و ارسال مجدد. کانال و پیام اصلی باید در دسترس همان ربات باشند.

## تنظیمات

```dotenv
BACKUP_DIR=backup
RESTORE_MAX_BYTES=2147483648
PG_TOOL_TIMEOUT=900
PG_DUMP_PATH=
PG_RESTORE_PATH=
```

حد حجم روی فایل آپلودی، بازشدن gzip و SQL استخراج‌شده از archive اعمال می‌شود. SQL حداکثر ۱۶ میلیون کاراکتر در هر خط و ۳۲ میلیون کاراکتر در یک statement پذیرفته می‌شود؛ برای دادهٔ بزرگ COPY مناسب است. ابزارهای باینری PostgreSQL جدا از وابستگی‌های pip نصب می‌شوند. توکن یا نام فایل کاربر وارد shell command نمی‌شود.

## تست‌ها

تست‌ها شامل دامپ با/بدون schema، COPY و انواع INSERT، جدول خالی، تفاوت نسخه، gzip/custom/tar، مدل قدیمی، مالکیت PK و userid، حفظ ID/bytea/Unicode/password/count، checksum، فایل ناقص، مالک ناموجود، rollback تزریق‌شده، پیش‌نمایش/تأیید/لغو، پاک‌سازی cache، invalidation هم‌زمان، reference منقضی و سقف دانلود هم‌زمان هستند. آزمون واقعی PostgreSQL فقط دیتابیس‌های موقت ساخته و حذف می‌کند؛ Telegram با mock بررسی می‌شود.

برای تست واقعی دو نسخه، CUTLY_TEST_POSTGRES_URL و CUTLY_TEST_POSTGRES_SECOND_URL را روی سرورهای آزمایشیِ قابل ایجاد دیتابیس تنظیم کنید. CUTLY_TEST_PG_DUMP_16 و CUTLY_TEST_PG_DUMP_18 مسیر client متناظر را مشخص می‌کنند؛ PG_RESTORE_PATH باید جدیدترین client باشد. CUTLY_TEST_REDIS_URL نیز باید Redis اختصاصی تست باشد. سپس `python -m pytest -q` را اجرا کنید.
