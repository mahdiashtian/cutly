# معماری Cutly و دلیل هر تصمیم

این سند توضیح می‌دهد کد چطور چیده شده و **چرا**. ساختار از پروژهٔ couplyo الهام گرفته
(لایه‌بندی، Unit of Work، کش cache-aside با Redis، Container به‌عنوان composition root)
و هرجا راه‌حل ساده‌تر یا درست‌تری وجود داشت، همان انتخاب شده است.

## لایه‌ها

```text
bot/            لایهٔ تلگرام: dispatcher، router، handlerها، متن‌ها، کیبوردها
worker/         Celery: کارهای طولانی و زمان‌بندی‌شده، بیرون از پروسهٔ ربات
services/       منطق کسب‌وکار؛ فقط با DTO کار می‌کند، نه با Telethon و نه با ORM
repositories/   دسترسی به داده: postgres (منبع حقیقت) و redis (کش و state)
schemas/        DTOهای Pydantic: تنها شکلی که بین لایه‌ها جابه‌جا و در Redis ذخیره می‌شود
db/             engine، مدل‌های ORM، Redis pool، کمک‌کارهای Alembic
core/           تنظیمات، enumها، زمان، امنیت (بدون وابستگی به هیچ لایهٔ دیگر)
container.py    تنها جایی که زیرساخت به سرویس‌ها وصل می‌شود (ربات و worker هر دو از آن استفاده می‌کنند)
```

قاعدهٔ وابستگی یک‌طرفه است: `bot/worker → services → repositories → db/schemas → core`.
سرویس‌ها Telethon را نمی‌شناسند؛ بنابراین بدون تلگرام تست می‌شوند و worker هم از همان سرویس‌ها استفاده می‌کند (DRY).

## کاملاً async و بدون توقف

| کار | کجا اجرا می‌شود | چرا |
| --- | --- | --- |
| پاسخ به پیام‌ها | پروسهٔ ربات، هر update در task خودش | کندی یک کاربر بقیه را معطل نمی‌کند |
| ارسال همگانی | Celery، صف `broadcasts` | ممکن است ساعت‌ها طول بکشد |
| حذف پیام بعد از ۳۰ ثانیه | Celery با `countdown` | با ری‌استارت ربات از بین نمی‌رود (قبلاً یک لیست در حافظه بود) |
| بک‌آپ، بررسی و اعمال بازیابی | Celery | کل دیتابیس را می‌خواند/بازنویسی می‌کند و CPU-bound است |
| شروع ارسال‌های زمان‌بندی‌شده | Celery Beat هر دقیقه | زمان‌بندی در جدول SQL است، نه در حافظهٔ APScheduler |
| هش رمز (scrypt) | `asyncio.to_thread` | CPU-bound است و نباید event loop را قفل کند |
| ارسال task به صف | `asyncio.to_thread(send_task)` | حتی I/O کوتاه Redis هم loop را مسدود نمی‌کند |

worker برای هر پروسه **یک** event loop، **یک** Container و **یک** کلاینت تلگرام می‌سازد
(`worker/runtime.py`) و بین taskها نگه می‌دارد. ساختن آن‌ها برای هر task یعنی یک pool جدید
و یک login تازه برای هر حذف پیام. کلاینت worker نشست جداگانه و `receive_updates=False` دارد،
پس با ربات سر فایل session یا updateها رقابت نمی‌کند.

## دیتابیس (طراحی از نو)

| جدول | تغییر نسبت به قبل | دلیل |
| --- | --- | --- |
| `users` | شناسهٔ تلگرام خودش کلید اصلی است؛ `is_superuser` و `is_staff` شدند `is_admin`؛ `phone_number` (هیچ‌وقت نوشته نمی‌شد) حذف شد؛ `access_hash` اضافه شد | یک index کمتر، یک join کمتر؛ worker بدون درخواست اضافه می‌تواند به کاربر پیام بدهد |
| `links` + `link_media` | قبلاً هر آیتم آلبوم یک ردیف `file` با کپی همهٔ تنظیمات و کدهای `CODE_partN` بود | نرمال‌سازی: تنظیمات و شمارنده یک‌جا روی لینک؛ ترتیب آیتم‌ها با `position` |
| `link_views` | به `link_id` اشاره می‌کند نه به رشتهٔ کد | FK و cascade واقعی؛ index برای لاگ هر کاربر و آمار ۲۴ ساعت |
| `mandatory_channels` | ستون `title` اضافه شد؛ `is_active` (همیشه true) حذف شد | عنوان یک بار هنگام افزودن خوانده می‌شود، نه هنگام هر بازسازی کش |
| `broadcasts` | وضعیت، زمان‌بندی، `cursor`، heartbeat و درخواست لغو در جدول | ادامه بعد از crash، لغو از هر پروسه، زمان‌بندی ماندگار |
| `bot_settings` | بدون تغییر | ساده و کافی |

نکته‌های مهم:

- **سقف دانلود دقیق است.** گرفتن سهمیه یک `UPDATE … WHERE count < max RETURNING` اتمیک است.
  کد قبلی رزرو را در حافظهٔ پروسه نگه می‌داشت و فقط برای یک پروسه درست بود. اگر ارسال شکست بخورد سهمیه برمی‌گردد.
- **فقط یک ارسال همگانی هم‌زمان**، با یک partial unique index روی `status = 'running'`؛ خود دیتابیس تضمین می‌کند.
- **رمز لینک‌ها هش می‌شود** (scrypt با salt). مالک در «شناسه پیگیری» فقط «دارد/ندارد» می‌بیند.
- **نوشتن `last_active_at`** با یک `SET NX EX` در Redis حداکثر هر ۵ دقیقه یک بار انجام می‌شود، نه روی هر پیام.
- enumها با `CHECK` constraint ذخیره می‌شوند؛ مقدار نامعتبر به دیتابیس نمی‌رسد.
- چون دادهٔ قبلی‌ای وجود ندارد، تاریخچهٔ migration یک فایل تمیز است (`0001_initial`) و هیچ کد تبدیل
  schema قدیمی نگه داشته نشده. تست `test_migrations_match_models` تضمین می‌کند خروجی migration دقیقاً همان مدل‌هاست.
- `python main.py` قبل از بالا آوردن workerها **یک بار** migration را اجرا می‌کند؛ هیچ دو پروسه‌ای هم‌زمان migrate نمی‌کنند.

### بهینه‌سازی‌های دیتابیس

| بهینه‌سازی | اثر |
| --- | --- |
| `eager_defaults` روی همهٔ مدل‌ها | مقدار `created_at` در همان `INSERT … RETURNING` برمی‌گردد؛ یک SELECT اضافه بعد از هر insert حذف شد |
| رابطهٔ `Link.media` با `lazy="raise"` و `selectinload` فقط هنگام نیاز | صفحهٔ تاریخچه دیگر ردیف‌های media (با file_reference) را بی‌دلیل بار نمی‌کند؛ lazy-load تصادفی خطا می‌دهد نه query پنهان |
| `fillfactor = 90` روی `links` و `users` (فقط PostgreSQL) | این دو جدول مدام درجا آپدیت می‌شوند (شمارندهٔ دانلود، زمان فعالیت)؛ فضای خالی صفحه اجازهٔ HOT update می‌دهد و هیچ index بازنویسی نمی‌شود |
| partial index `ix_users_admins` (`WHERE is_admin`) | فهرست ادمین‌ها بدون اسکن کل کاربران؛ کاربران عادی هزینه‌ای برای این index ندارند |
| `UPDATE` سادهٔ زمان فعالیت بدون `RETURNING` | مسیر پرتکرار ردیفی را که کسی نمی‌خواند برنمی‌گرداند |
| SQLite (توسعه): `synchronous=NORMAL` با WAL | بدون خطر خرابی، fsync برای هر commit حذف می‌شود |

indexهای موجود با queryها تطبیق داده شده‌اند: `(owner_id, created_at)` برای تاریخچه و شمارش لینک‌ها،
`(viewer_id, link_id, viewed_at)` برای لاگ کاربر، `viewed_at` و `created_at` برای آمار ۲۴ ساعت،
`link_id` تا حذف لینک بدون اسکن کامل cascade شود، `(status, scheduled_at)` برای پیدا کردن ارسال‌های سررسید.
هیچ index اضافه‌ای که فقط هزینهٔ نوشتن داشته باشد نگه داشته نشده است.

## کش Redis (مثل couplyo)

سه namespace جدا در `repositories/redis/keys.py`:

| prefix | محتوا | رفتار |
| --- | --- | --- |
| `cutly:cache:v1:*` | کپی ردیف‌های SQL: کاربر، لینک (با media)، کانال‌ها، تنظیمات، نشانگر عضویت | قابل پاک شدن در هر زمان؛ بعد از restore پاک می‌شود |
| `cutly:state:*` | گفتگوها، جلسهٔ آپلود، بازیابی در انتظار تأیید، حالت تعمیر | هیچ‌جای دیگری وجود ندارد؛ هیچ‌وقت با کش پاک نمی‌شود |
| `cutly:ops:*` | نشانگرهای کوتاه‌عمر (throttle فعالیت) | TTL خودشان |

- **cache-aside برای خواندن، write-through برای نوشتن** (`services/base.py`): خطای Redis هیچ درخواستی را خراب نمی‌کند؛ خواندن به SQL برمی‌گردد.
- **negative caching**: کد لینکی که وجود ندارد هم کش می‌شود تا حدس زدن کدها به دیتابیس نرسد.
- payloadی که با DTO فعلی نخواند (deploy قدیمی، نوع اشتباه) مثل miss رفتار می‌شود و از SQL بازنویسی می‌شود.
- `download_count` عمداً در کش نیست؛ هر دانلود تغییرش می‌دهد و مرجعش SQL است.
- **عضویت اجباری**: فقط جواب مثبت کش می‌شود (کش «عضو نیست» کاربری را که تازه عضو شده قفل نگه می‌داشت).
  مقدار ذخیره‌شده اثرانگشت مجموعهٔ کانال‌هاست؛ تغییر کانال‌ها همهٔ نشانگرها را بدون SCAN باطل می‌کند.
- در شروع فقط داده‌های کوچک و پرمصرف (کانال‌ها، تنظیمات) گرم می‌شوند؛ کاربر و لینک هنگام اولین خواندن.
- دو Redis (مثل couplyo): cache با `allkeys-lru` و state با AOF و `noeviction`؛ با یک Redis هم کار می‌کند.
- pool از نوع blocking با timeout است تا انفجار درخواست‌ها صف شود، نه اینکه همه را به دیتابیس بریزد.

مسابقهٔ نادر «خواندن قدیمی بعد از نوشتن تازه» (همان trade-off couplyo) با TTL یک‌روزه محدود می‌شود.
نسخه‌های token-دار کد قبلی این را حذف می‌کردند اما پیچیدگی زیادی داشتند؛ برای دادهٔ مهم (شمارنده) از کش استفاده نمی‌شود.

## مسیریابی ربات

به‌جای ~۶۰ handler که هرکدام با فیلترش state را دوباره می‌خواند، `bot/dispatcher.py` state را **یک بار**
می‌خواند و `bot/router.py` با دو lookup دیکشنری handler را پیدا می‌کند: اول متن دکمه/دستور (که می‌تواند به
stateهای خاصی محدود باشد)، بعد handler همان state. دکمهٔ شناخته‌شده‌ای که در state فعلی معنا ندارد نادیده
گرفته می‌شود (مثل فیلترهای قبلی). دکمهٔ «بازگشت» از یک جدول والد (`bot/states.py`) استفاده می‌کند.

## بک‌آپ و بازیابی

- **بک‌آپ کامل**: `pg_dump`. **بک‌آپ داده**: `jsonl.gz` جریانی با checksum و شمارش ردیف‌ها و شمارهٔ revision.
- **بازیابی**: فایل در یک SQLite موقت با **همان revision بک‌آپ** بارگذاری می‌شود و بعد همان migrationهای
  همیشگی تا `head` اجرا می‌شوند. یعنی بک‌آپی که قبل از یک تغییر schema در آینده گرفته شده با همان کد
  migration تبدیل می‌شود و مبدل دستیِ دومی وجود ندارد. سپس ادمین تعداد ردیف‌ها را می‌بیند و تأیید می‌کند؛ جایگزینی در یک تراکنش انجام
  می‌شود و قبلش یک نسخهٔ ایمنی گرفته می‌شود. در این مدت پرچم maintenance در Redis همهٔ پروسه‌ها را متوقف می‌کند.
- پارس کردن SQL خام `pg_dump` (۸۴۰ خط کد قبلی) حذف شد: اجرای SQL دلخواه کار `psql`/`pg_restore` است و
  بک‌آپ کامل همیشه با همان ابزارها بازیابی می‌شود.

## امنیت

اصل کلی: **امن به‌طور پیش‌فرض**. هر محافظت در یک نقطهٔ مشترک (`bot/dispatcher.py`) برای هر update
(پیام، آلبوم، دکمهٔ inline) اجرا می‌شود و به یادآوری در هر handler وابسته نیست.

| تهدید | محافظت |
| --- | --- |
| دسترسی کاربر عادی به پنل ادمین | هر route یک سطح دسترسی دارد (`Access.USER/ADMIN/OWNER`) و قبل از handler بررسی می‌شود. router هنگام بالا آمدن ربات خطا می‌دهد اگر routeی برای stateهای ادمین بدون سطح ادمین ثبت شود؛ فراموش کردن یک چک در کد جدید به production نمی‌رسد. کاربر عادی هیچ پاسخی از دکمه‌های ادمین نمی‌گیرد (اطلاعاتی لو نمی‌رود) |
| ادمینی که در وسط کار عزل شده | حق دسترسی روی **هر پیام** دوباره بررسی می‌شود، نه فقط هنگام ورود به پنل؛ دکمه‌های inline پیام‌های قدیمی هم در هر کلیک بررسی می‌شوند |
| ارتقای دسترسی توسط ادمین معمولی | مدیریت ادمین‌ها، بک‌آپ (کل دیتابیس) و بازیابی (جایگزینی کل داده) فقط برای مالک (`ADMIN_MASTER`) است |
| دور زدن عضویت اجباری | عضویت در **هر مرحله** از هر جریان کاربری بررسی می‌شود (قبلاً فقط اولین پیام؛ می‌شد بعد از درخواست رمز از کانال خارج شد و فایل را گرفت). آلبوم‌ها و دکمه‌های inline هم شامل‌اند. خطای تلگرام = عضو نیست (fail closed) |
| حدس زدن رمز لینک | حداکثر ۵ تلاش برای هر کاربر و هر لینک در ۱۵ دقیقه؛ شمارش قبل از scrypt انجام می‌شود تا قفل‌شده هزینهٔ CPU نداشته باشد |
| سیل پیام (flood) | حداکثر ۳۰ update در ۱۰ ثانیه برای هر کاربر؛ بیشتر از آن دور ریخته می‌شود و فقط یک بار اطلاع داده می‌شود |
| حدس زدن یا دستکاری کد لینک | کدها ۱۵ کاراکتر تصادفی با `secrets` هستند (۶۲^۱۵ حالت). ورودی غیر از `[A-Za-z0-9]{1,32}` قبل از رسیدن به کش و دیتابیس رد می‌شود؛ کد ناموجود فقط ۵ دقیقه کش می‌شود تا کدهای تصادفی حافظه را پر نکنند |
| عبور از سقف دانلود/انقضا | گرفتن سهمیه یک UPDATE اتمیک با شرط انقضا و سقف است؛ هم‌زمانی هم آن را دور نمی‌زند |
| عبور از سقف فایل‌های یک لینک | افزودن به جلسهٔ آپلود اتمیک است و مازاد بلافاصله حذف می‌شود |
| دستکاری لینک دیگران | حذف، کپشن، رمز و اطلاعات لینک همه بر اساس مالک فیلتر می‌شوند؛ دادهٔ دکمه‌های inline فقط شمارهٔ صفحه است و کاربر از فرستندهٔ واقعی تعیین می‌شود |
| افشای رمزها | رمز لینک‌ها با scrypt و salt هش می‌شود و مقایسه زمان‌ثابت است؛ حداکثر طول ۱۲۸ کاراکتر |
| فایل بک‌آپ مخرب | فقط مالک می‌تواند بازیابی کند؛ فایل ابتدا در یک SQLite جدا با همهٔ constraintها اعتبارسنجی می‌شود؛ checksum، شمارش ردیف‌ها، ستون و جدول ناشناخته، حجم بازشدهٔ gzip و طول خط کنترل می‌شود؛ همهٔ queryها پارامتری‌اند |
| اجرای کد از صف | Celery فقط JSON می‌پذیرد (نه pickle) |
| دسترسی شبکه به سرویس‌ها | PostgreSQL و Redis فقط روی `127.0.0.1` منتشر می‌شوند |

برای production: رمز PostgreSQL را در `docker-compose.yml` و `DB_URL` عوض کنید و فایل `.env`
(توکن ربات) و فایل‌های `*.session` را محرمانه نگه دارید؛ هر دو در `.gitignore` هستند.

## اجرا

مثل couplyo: فقط زیرساخت در Docker است و خود پروژه روی میزبان اجرا می‌شود.

- `docker compose up -d` سه سرویس را بالا می‌آورد: PostgreSQL روی `25432`، Redis کش روی `26379`،
  Redis state روی `26380` (همه فقط روی localhost). پورت‌ها ثابت‌اند چون پورت‌های پیش‌فرض روی سیستم توسعه
  اشغال‌اند و همین مقادیر در `.env.example` و پیش‌فرض‌های `core/config.py` آمده‌اند.
- `python main.py` به ترتیب: migration را اجرا می‌کند، worker صف `default`، worker صف `broadcasts` و
  beat را به‌عنوان پروسه‌های جدا بالا می‌آورد (`worker/processes.py`) و سپس ربات را اجرا می‌کند. با Ctrl+C
  همه با هم متوقف می‌شوند. پروسهٔ جدا (نه thread) یعنی کار سنگین worker هرگز ربات را کند نمی‌کند و crash یکی بقیه را نمی‌کشد.
- worker ارسال همگانی جداست تا ارسالی که ساعت‌ها طول می‌کشد، حذف پیام‌های ۳۰ ثانیه‌ای را معطل نکند.
  روی ویندوز (که fork ندارد) worker پیش‌فرض با pool از نوع solo اجرا می‌شود.
- برای اجرای workerها روی ماشین‌های دیگر، `EMBEDDED_WORKERS=false` و دستورهای `worker/app.py`.

## تغییرات رفتاری (عمدی)

- تاریخچهٔ آپلود با دکمه‌های صفحه‌بندی نمایش داده می‌شود، نه ارسال یک پیام برای هر ۵ لینک (که برای کاربران پرفایل سیل پیام بود).
- رمز لینک‌ها در «شناسه پیگیری» نمایش داده نمی‌شود (هش شده‌اند).
- آپلود فایلِ دارای کپشن دیگر رد نمی‌شود (باگ قبلی: `message.text` کپشن را هم شامل می‌شد).
- هر لینک حداکثر `UPLOAD_MAX_FILES` (پیش‌فرض ۱۰۰) آیتم دارد تا اندازهٔ state و تعداد پیام‌های تحویل محدود بماند.
- افزودن کانال اجباری بررسی می‌کند ربات به کانال دسترسی دارد؛ کانالی که ربات نمی‌بیند همهٔ کاربران را قفل می‌کرد.
- برای مخاطب «اعضای کانال»، عضویت هنگام ارسال بررسی می‌شود (نه با هزاران درخواست داخل handler).
- «❌ لغو ارسال» ارسال‌های زمان‌بندی‌شده را هم لغو می‌کند، چون حالا با ری‌استارت از بین نمی‌روند.
- نرخ ارسال همگانی با `BROADCAST_RATE_PER_SECOND` تنظیم می‌شود و FloodWait همهٔ ارسال‌ها را با هم متوقف می‌کند.
