# کارایی و ساختار کش

سیاست کسب‌وکار، اسکیمای Alembic و وابستگی Telethon 1.45.0 حفظ شده‌اند. این بازبینی مسیرهای هم‌زمانی، بازیابی، رشد حافظه و هزینهٔ query را اصلاح می‌کند. نتیجهٔ آزمون‌ها در [گزارش اعتبارسنجی](verification.md) ثبت می‌شود.

## مرجع داده و طول عمر

| داده | محل و طول عمر | تغییر و اعتبارسنجی |
| --- | --- | --- |
| شناسهٔ کاربران | Redis sorted set، بدون TTL؛ marker برای کامل‌بودن نمایه | هر ثبت‌نام یک ZADD NX؛ تکمیل از SQL با merge و WATCH؛ حذف/تغییر userid کل نمایه را باطل می‌کند |
| پروفایل، نقش و زمان فعالیت | Redis، ۶۰۰ ثانیه | token اختصاصی کاربر؛ تغییر نقش یا رکورد، همان کاربر را باطل می‌کند؛ زمان فعالیت به صورت افزایشی و بدون تمدید TTL نوشته می‌شود |
| شناسهٔ ادمین‌ها | snapshot Redis، ۳۰۰ ثانیه | token ادمین‌ها؛ رکوردهای بازگشتی از SQL خوانده می‌شوند |
| شناسه، access_hash، file_reference، کپشن و مشخصات فایل | snapshot Redis، ۳۰۰ ثانیه | token فایل؛ تغییر code/album هر دو مشخصات قبلی و جدید را باطل می‌کند |
| اعضای مرتب آلبوم | snapshot Redis، ۳۰۰ ثانیه | token آلبوم؛ جابه‌جایی، درج یا حذف عضو، آلبوم مربوط را باطل می‌کند |
| تنظیمات کپشن | snapshot Redis، ۳۰۰ ثانیه | تغییر تنظیمات token را عوض می‌کند |
| تنظیمات کانال‌های قفل | Redis، ۳۰۰ ثانیه؛ حافظهٔ محلی ۳۰ ثانیه | کنترل token و revision محلی؛ انتشار نتیجه تنها اگر تنظیمات حین ساخت عوض نشده باشند |
| شمارنده، سقف دانلود، انقضا و آمار | SQL | شمارندهٔ گرم هم از SQL خوانده می‌شود؛ رزرو موقت وارد دیتابیس یا بک‌آپ نمی‌شود |
| عضویت واقعی در کانال | Telegram | برای هر بررسی دسترسی خوانده می‌شود |

tokenهای فایل، آلبوم و پروفایل ۱۲۰۰ ثانیه عمر دارند؛ چند token عمومی ثابت باقی می‌مانند. ایجاد token جدید از UUID استفاده می‌کند؛ حذف یا eviction آن نمی‌تواند snapshot قدیمی را دوباره معتبر کند. همهٔ snapshotها فقط با token گرفته‌شده پیش از خواندن SQL ذخیره می‌شوند. اگر گرفتن token شکست خورده باشد، نتیجهٔ قدیمی پس از بازگشت Redis ذخیره نمی‌شود.

نمایهٔ کاربران یک عضو sentinel دارد تا eviction نمایه و سپس یک افزودن جزئی، به عنوان فهرست کامل پذیرفته نشود. JSONهای نسخهٔ قبلی هنوز قابل خواندن‌اند و در افزودن بعدی به ساختار جدید تبدیل می‌شوند. نمایهٔ کامل در اولین نیاز از SQL بازسازی می‌شود؛ هیچ درخواست ثبت‌نامی کل فهرست ۱۰۰ هزار کاربر را بازنویسی نمی‌کند.

## هم‌زمانی و حافظه

خواندن سرد پروفایل، متادیتای فایل، آلبوم و تنظیمات، یک loader مشترک برای هر کلید دارد. قفل‌ها فقط تا پایان درخواست‌های همان کلید نگهداری می‌شوند. دانلودها روی کدهای خود قفل می‌گیرند؛ درخواست یک فایل کند، دانلود لینک مستقل را متوقف نمی‌کند. ترتیب ثابت قفل‌های آلبوم مانع بن‌بست می‌شود. شکست ارسال و لغو انتظار برای ثبت شمارنده، رزرو را آزاد می‌کند.

ساخت عنوان کانال و بررسی مخاطبان عضو کانال با پنج worker انجام می‌شود؛ حذف پیام با ده worker. تعداد taskها با تعداد کل کاربران رشد نمی‌کند. وضعیت و object گفتگو بعد از بازگشت به حالت idle از dict حذف می‌شوند. فهرست کل شناسه‌های کاربران و نتیجهٔ انتخاب مخاطبان همچنان به اندازهٔ کاربران حافظه مصرف می‌کنند؛ این تغییر ادعای مصرف حافظهٔ ثابت برای ارسال همگانی ندارد.

رزرو دانلود و وضعیت گفتگو برای **یک process ربات** طراحی شده‌اند. اجرای چند process روی دیتابیس مشترک برای سقف دانلود دقیق نیازمند رزرو توزیع‌شده است. هیچ محدودیتی به نرخ پیام‌ها اضافه نشده و ثبت فعالیت هر پیام در SQL حفظ شده است.

## دیتابیس و اتصال‌ها

آمار داشبورد یک SELECT با subqueryهای تجمیعی است؛ فرمول‌ها و پنجره‌های قبلی را با یک snapshot می‌خواند. مخاطبان جدید، فعال و غیرفعال در SQL فیلتر می‌شوند. indexهای فعلی برای مالک/تاریخ فایل، کد فایل و viewer/time لاگ حفظ شده‌اند. index جدید روی last_activity_at اضافه نشده چون هر پیام آن را تغییر می‌دهد و هزینهٔ write ایجاد می‌کند. آزمون دادهٔ بزرگ استفاده از index موجود viewer را با EXPLAIN بررسی می‌کند.

درج کل جلسهٔ آپلود در یک تراکنش انجام می‌شود؛ خطا وسط آلبوم هیچ عضو جدیدی باقی نمی‌گذارد. خواندن شمارنده‌ها، رزرو و افزایش آلبوم بزرگ در دسته‌های ۹۰۰ شناسه انجام می‌شوند تا پارامتر اضافی UPDATE هم زیر سقف ۹۹۹ SQLite باقی بماند. افزایش چند دسته همچنان در یک تراکنش است.

| تنظیم | پیش‌فرض | کاربرد |
| --- | --- | --- |
| DB_POOL_SIZE | ۱۰ | اتصال‌های پایهٔ PostgreSQL در هر process |
| DB_MAX_OVERFLOW | ۲۰ | اتصال‌های اضافی مجاز PostgreSQL |
| DB_POOL_TIMEOUT | ۳۰ ثانیه | انتظار برای اتصال آزاد دیتابیس |
| DB_POOL_RECYCLE | ۱۸۰۰ ثانیه | عمر اتصال پیش از بازیافت؛ pre_ping و LIFO فعال‌اند |
| DB_SQLITE_WAL | true | اجازهٔ ادامهٔ خواندن snapshot هنگام write؛ busy_timeout سی ثانیه و foreign_keys فعال‌اند |
| REDIS_MAX_CONNECTIONS | ۶۴ | سقف اتصال Redis در هر process |
| REDIS_POOL_TIMEOUT | ۵ ثانیه | انتظار pool Redis برای اتصال آزاد |
| REDIS_SOCKET_TIMEOUT | ۲ ثانیه | محدودیت انتظار پاسخ Redis |

این مقادیر ظرفیت قطعی سرور نیستند؛ سقف مجموع اتصال همهٔ processها باید در تنظیمات PostgreSQL و Redis جا شود. افزایش pool بدون اندازه‌گیری الزاماً سرعت بیشتری ایجاد نمی‌کند. گزینه‌ها در [.env.example](../.env.example) ثبت شده‌اند.

شکست invalidation باعث bypass کش و ساخت marker پایدار reset می‌شود. job هر ۳۰ ثانیه اتصال را دوباره بررسی می‌کند؛ قبل از فعال‌شدن، فقط namespace cutly:* با SCAN/UNLINK پاک می‌شود. کلیدهای برنامه‌های دیگر باقی می‌مانند. بازیابی دیتابیس پایان مرحلهٔ SQL و cache هر عملیات را انتظار می‌کشد و با reconnect هم‌زمان تداخل ندارد.

## آزمون‌های بار

test_scale_integration.py روی PostgreSQL 16.15 و 18.6، در هر اجرا ۱۰۰٬۰۰۱ کاربر، ۱۰۰٬۰۰۱ فایل و ۲۰۰٬۰۰۰ لاگ مصنوعی می‌سازد. آمار یک query، صفحه‌بندی تاریخچه و انتخاب مخاطب بررسی می‌شوند. از ۱۰۰۰ دانلود هم‌زمان یک لینک با سقف ۳، دقیقاً سه ارسال موفق و شمارندهٔ نهایی ۳ لازم است؛ هیچ رزرو یا قفل باقی نمی‌ماند.

آزمون Redis واقعی با چهار اتصال، نمایهٔ ۱۰۰ هزار کاربر، ۱۰۰۰ افزودن و ۱۰۰۰ خواندن پروفایل هم‌زمان را بررسی می‌کند. تست‌های واحد جداگانه پرشدن سرد با ۳۰۰ خواننده، snapshot کهنه بعد از تغییر نقش، eviction، خطای اتصال، لغو دوباره، خطای عنوان کانال، اتمیک‌بودن آلبوم و بازیابی لغوشده را پوشش می‌دهند. این آزمون‌ها ادعای نرخ ارسال واقعی Telegram یا ظرفیت محیط production نیستند؛ ارسال Telegram با test double انجام می‌شود.
